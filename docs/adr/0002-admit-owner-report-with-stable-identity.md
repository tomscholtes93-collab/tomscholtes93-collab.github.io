# 0002. Publish the supplied owner report through existing content and operational ownership

## Context

G183 must include the complete sourced October 2026 baseline, granular sector roadmap through 2046 and substantial imagined future story. INTENT records the completed 80,088-byte shared-artifact handoff and its exact source hash, source ledger completion, independent technical acceptance and Tom's publication authorization under option A. These establish different facts. They do not establish that Tom personally reviewed the report bytes or that a transformed website candidate has passed technical review. Independently built import, presentation and publication work could otherwise disagree about source authority, edition availability or release acceptance.

## Decision

Use the supplied report identified in DESIGN as the candidate input. The research owner retains authority over substantive content. The importer may perform the already accepted heading normalization, contents and reading aids, accurate AI-authorship disclosure, metadata and removal of the opening direct address to Tom. It preserves all substantive sections, citations, reading links and the entire story. A rerunnable source/render comparison accounts for those transformations against the original hash. Source changes or transformations outside the accepted scope require refreshed affected technical evidence. No new personal approval is required.

Use the existing content publication system, initially the notes collection, with one stable unlocalized slug and actual locale availability shared by routes, discovery, feeds, metadata and comments. Import explicitly as draft. Under Tom's existing authorization, the publisher may prepare the intended published state on an isolated unpublished branch so independent review covers the exact final publication candidate. This project-specific authorization supersedes any interpretation of the older draft convention that would demand another personal status flip. The disclosure requirement and independent technical reviews remain applicable.

Keep the handoff procedural and its evidence in the existing operational ledger. The publication owner references original source acceptance, producer and integrated-candidate reviews, quality/browser results, authenticated access, workflow results and live verification. The importer accepts the supported source file and expected hash; it does not consume a new release contract. Product scripts may check source/render fidelity and live report content. They do not adjudicate reviews, validate credentials, interpret workflow identity or maintain release stages.

## Alternatives

A dedicated report application or parallel content authority would duplicate publication status, locale routing and metadata for one deliverable. Fetching research-job storage during builds would couple the site to inaccessible operational storage and allow source changes outside the reviewed candidate. A local copy through the supported handoff avoids both costs.

An executable release-readiness subsystem could centralize evidence checks, but it would duplicate the existing Factory and publisher responsibilities and create another acceptance authority. Synthetic readiness tests would prove that new checker, not actual publication. The intent explicitly chooses a one-off handoff using existing records instead.

Requiring Tom to approve exact bytes again would add an unsupported personal gate after recorded publication authorization and technical acceptance. Treating source acceptance alone as approval of the integrated website would make the opposite error. The existing independent technical review sequence preserves that distinction.

## Consequences

Site-experience work remains independently implementable and reviewable. The completed report handoff is no longer described as an awaited external prerequisite. A missing or mismatched local copy is an access or integrity defect to resolve through the supported handoff, not a reason to restart research or request personal approval.

Existing GitHub write access remains a separate, evidenced deployment prerequisite. The publication owner records the reviewed integrated commit/tree and source hash, deploys through the established workflow, and retains actual live-content evidence. The live check rejects wrong editions, missing sections, homepage fallbacks and broken report assets or fragments. It does not consume or reinterpret reviewer and credential records.

The release evidence includes the previously deployed commit and concrete revert commands for the actual release commits, preserving unrelated later work, followed by redeployment and renewed live checks. A changed candidate needs refreshed affected evidence. Original failures and actual review attempts remain retained. Operational records stay outside public content and build output; readers receive the complete report, useful citations and accurate authorship disclosure.
