> Generated by a multi-agent design and review workflow on 2026-08-01, then applied and verified against the built site. Angle: what a reading pass to this site's essays actually changed, measured before and after.

The essays on this site were set in a user interface. Not metaphorically. The body copy used the same size token as the card labels and the metadata rows, which is a sensible size for a button and a poor one for six thousand words.

The number that made this concrete is the measure: the count of characters on an average line. Before this pass it was **95.4**, and at the least forgiving viewport, 98.4. The conventional comfortable band is 60 to 75. That band deserves a caveat, and it gets one below, but the gap was large enough that the caveat does not rescue it.

**A measure is not a width.** This is the part worth keeping even if every other number here is wrong. The old column was declared in pixels: a maximum width of 46rem, and separately a font size. Two independent declarations, and the character count was simply whatever fell out of dividing one by the other. Change either and the reading experience moves, silently, in a direction nobody chose.

The pass inverts that. The character count is now the declared quantity and the pixel width is derived from it:

```css
--adv: 0.4675em;
--cpl: 70;
--measure: calc(var(--cpl) * var(--adv));
```

`--cpl` is characters per line. `--adv` is the average character advance, and it is measured rather than assumed: 0.4675 em over 31,986 characters of the actual published corpus, with the frontmatter and markdown stripped. Because the whole expression is in em of the reading size, the character count now holds at every viewport, every zoom level, and every density setting. The column width is what changes.

The first draft of this used 0.4942 em, taken from a pangram-weighted sample. A pangram over-represents the wide rare letters, so the sampled mean was inflated by about six percent, and the declared 74 characters was actually delivering 78. The error was found because someone re-measured against the real text rather than the convenient text. Both figures were reproduced independently before the change shipped.

**The same mechanism fixes Russian, which is the part that surprised me.** Cyrillic in this typeface has an average advance of 0.5396 em against Latin's 0.4675. If the column is declared in pixels, Russian silently runs about sixty characters where English runs seventy. Declaring the character count instead, and giving Russian its own advance constant, produces a Russian column that is 737 pixels wide against English's 638 and holds exactly the same seventy characters. The invariant is the reading experience. The width is an implementation detail.

There is a related problem the pass could not solve by arithmetic. The display typeface used for titles contains **zero Cyrillic codepoints**: 206 glyphs, and the letter А is not among them. Every Russian title on this site was therefore rendering in whatever serif the reader's operating system happened to supply, and a redesign nine days earlier had made those titles larger, which made the fallback more visible rather than less. The replacement is a light grade of the body sans, chosen by measurement: its stem weight is 0.0664 em against the serif's 0.0680, a match within two and a half percent, where the regular grade is 29 percent too heavy and the medium grade 58 percent. The intuitive move for a display role is to reach for more weight. For this pairing that is exactly backwards, because the serif reads light on the page precisely because half its strokes are hairlines.

**The structure was already in the writing.** Six of the seven essays contain no headings at all. But five of them contain twenty-two paragraphs that open with a bold lead-in, and in every single file the number of paragraph-initial bold spans equals the total number of bold spans. Bold is used in this corpus for exactly one thing. No stylesheet rule reached those spans, so the only hierarchy the author had actually written rendered as default browser bold, and in Russian as a synthetic smear. Styling them as run-in heads, with a longer interval before each, adds structure without inventing any.

Paragraph spacing had the same shape of problem. The gap between paragraphs was 0.626 of a line box, which means paragraph boundaries were registering more weakly than line boundaries. That is the mechanism that turns a nineteen-hundred-character paragraph into a slab. Setting the interval to exactly one line box costs one token.

**Looking for the typography turned up eleven defects that had nothing to do with it.** The notes index rendered visually empty with JavaScript disabled, because every row was hidden until an observer un-hid it. The accent colour system was dead code: it was written as an inline style, which outranks the attribute selector the palette was defined with, so eight of fifteen reachable theme-and-colour combinations rendered below the accessibility floor, the worst of them at 1.03 to 1, which is the background colour. The back-link arrow was a character present in none of the fonts this site ships. The index masthead had been rendering 184 pixels wider than the list beneath it.

Six of those share one cause, and it is worth naming because it predicts where the next one will be: **two mechanisms expressing the same intent, with the winner decided by something nobody checked.** An inline style against an attribute selector. An element rule against a class the markup explicitly asked for. A script against a component. Fixing instances does not retire the class of fault.

Two honest caveats. The 60-to-75 band is the one load-bearing figure here that is a convention rather than a measurement; under a looser band the case for narrowing the column weakens considerably, though every defect above is real regardless. And one proposal did not survive its own test: sizing each index title by its word count produced six titles within five pixels of each other, which reads as wobble rather than ranking, so the word count is printed as a number instead. It is a better answer anyway. A reader can read a number. Nobody can read a 1.2 pixel difference.
